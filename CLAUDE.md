# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Screepy is a TypeScript-based AI bot for the game [Screeps](https://screeps.com/). The code compiles to JavaScript and gets deployed to Screeps servers where it runs autonomously to control game entities (creeps, spawns, towers). Since October 2026 its economy core follows Hivemind's model (roles, spawn options, resource dispatcher, room planner), ported from Hivemind (MIT, see `THIRD_PARTY_NOTICES.md`). Remote mining (milestones 2-3), CPU throttling (4), the full planner and base defense (5) and expansion (6) follow Hivemind too; scouting and the market remain from the previous design. Offense is ours to design (open-source bots keep it private).

## Local Test Server

Verify changes in a real engine before deploying (requires Docker Desktop and a valid Steam API key in `config.yml`):

```bash
docker compose up -d                       # start the local server (first start installs deps, ~3 min)
npm run test:server                        # build, deploy, respawn user "screepy", run 3000 ticks, PASS/FAIL report
npm run test:server -- --ticks 5000 --min-rcl 3
npm run test:server -- --code other/dist/main.js   # test another bundle (e.g. baseline from a git worktree)
npm run test:server -- --room W7N3                  # pick the room (default: first free 2-source room)
npm run test:server -- --list-rooms                 # list candidate rooms with spawn-to-sources range, touches nothing
npm run test:server -- --memory '{"foo":1}'          # initial Memory
npm run test:server -- --preset rcl4                # start from a fast-forwarded room (RCL 4, storage, extensions)
CODES="before=a.js after=dist/main.js" RUNS=2 bash scripts/compare.sh   # bundles x rooms x runs, mean points
npm run inspect:server                     # live snapshot: creeps, structures, errors
npm run inspect:server -- --memory rooms   # dump a Memory path
npm run test:server -- --client            # also open the steamless client on the tested room
npm run watch:server                       # from any other session/worktree: client + progress of the run in progress
```

- Runs are close to deterministic (two runs of the same bundle and room differ by ~1%), so one run per configuration is enough for A/B tests.
- Hivemind rework benchmark: see "Economy core" below. Hivemind 3.0.0 reference (8000 ticks): W7N3 107085, W9N5 189, W1N3 20300.
- Benchmark on several rooms (easy W7N3, medium W9N5, hard W1N3 where sources are ~30 tiles away): tuning on a single room overfits.
- Watching: the harness publishes the run state on the server (redis key `pserver:run`, see `scripts/pserver-lib.mjs`), so `watch:server` follows a run started from another session or worktree (opens the client on the tested room, prints progress and the final PASS/FAIL). `--no-client` for progress only. The compose project is named `screepy` so every worktree talks to the same server.
- One run at a time: the test user is shared, `test:server` refuses to start while another session's run is in progress (`--force` to replace it).
- Steamless client: `screeps-steamless-client` (via npx) serves the official client from Steam's `package.nw` (Screeps must be installed through Steam; found in Steam libraries, or `--package <path>` / `SCREEPS_NW_PACKAGE`), at `http://localhost:8080/(http://localhost:21025)/`, reused if already running. Log in as `screepy` / `screepy`. With `--client` the harness stays up after the report until Ctrl+C; add `--tick-ms 200` to slow the run down enough to follow it.

- Checks: no module errors, RCL reached, creep count, avg CPU, task failure ratio. Reports saved to `test-results/`.
- The bot writes `Memory.stats` (`src/utils/stats.ts`, `countStat()` for custom counters) and `Memory.moduleErrors` (ModuleManager).
- RCL/creeps are read from the server's room objects, so baseline bundles without `Memory.stats` can still be compared.
- Speed: the harness sets `system.setTickDuration(1)` (as fast as the engine goes, ~50 ms/tick). `config.yml` uses `processors: 2` / `runnerThreads: 2`: with 16 processors and one active room, redis coordination made ticks ~4x slower.
- Server quirks: `screepsmod-auth` is pinned to 2.8.3 in `config.yml` (2.9+ crashes with screepsmod-mongo); the admin CLI (port 21026) is only reachable from inside the container, the harness uses `docker compose exec`.

### Mockup (fast)

In-process engine (`screeps-server-mockup` master, vendored built in `scripts/mockup/vendor/`, same engine as the private server: screeps 4.3.0 on Node 24) in a dedicated Docker image `screepy-mockup` (built on first use, ~4 min; `@screeps/driver` compiles native code, no C++ toolchain needed on the host). Independent from the compose stack: runs can go in parallel. ~100 ticks/s on W7N3 (~10 ms/tick over 3000 ticks, ~17 ms/tick over 8000 ticks with 3 runs in parallel; about half of it is the bot own CPU); runs are nearly deterministic (the bot's own randomness, `_.sample`, gives a few % between runs).

```bash
npm run test:mockup                                    # build, 3000 ticks on W7N3, same PASS/FAIL checks as test:server
npm run test:mockup -- --code test-results/bundles/before-ac17616.js --room W1N3 --ticks 8000
npm run test:mockup -- --memory '{"foo":1}' --verbose   # initial Memory, print the bot console
npm run test:mockup -- --dump-memory --memory @test-results/x-memory.json  # Memory + segments at the end in <report>-memory.json; start from a dump
npm run test:mockup -- --list-rooms                    # rooms with a fixture
npm run test:mockup -- --profile                       # + wall ms/tick per main loop stage and CPU per engine process
npm run test:mockup -- --cpu-limit 13                  # lower the bot's CPU limit (13 code CPU ~ 20 official CPU with intents)
npm run test:mockup -- --raid 9000:smallMelee+smallRanged,15000:bigMelee+bigRanged   # invader raids (backend bodies), outcome in the report
npm run test:mockup -- --raid 13500:smallMelee@W7N4   # raid in another room of the fixture (a remote)
npm run test:mockup -- --raid '13500:smallMelee*@W7N4'   # "*": boosted like the backend's invaders (GO, UH, KO, ZH, LO); quote it in zsh
npm run test:mockup -- --preset rcl4 --enemy W8N3:5   # quick fast-forward at tick 1 (rcl4/rcl5/rcl7: storage, checkerboard extensions, containers) against an enemy base
npm run test:mockup -- --preset rcl4 --stronghold W7N4:1   # invader stronghold (bunker template, deploys at tick 5)
npm run test:mockup -- --preset rcl6 --ticks 4000      # plan-based fast-forward (rcl6, rcl8, plan5..plan8): built from the bot's plan once stored (terminal, minerals, labs)
npm run test:mockup -- --no-fast                       # unpatched engine (upstream main loop, 1 processor, TCP): A/B check of the speed-ups
npm run test:mockup -- --ticks 22000 --save-state test-results/states/W7N3-22k.json   # save the world (objects, game time, Memory) at the end
npm run test:mockup -- --load-state test-results/states/W7N3-22k.json --ticks 15000   # start from it (same room; Memory.stats counters and moduleErrors reset)
npm run test:mockup -- --load-state test-results/states/W7N3-22k.json --set-rcl 5     # ... with the controller forced to RCL 5 (progress 0): RCL 5+ code from an RCL 4 economy
CODES="before=a.js after=dist/main.js" RUNS=1 JOBS=6 bash scripts/mockup/compare.sh   # like scripts/compare.sh, parallel
node scripts/mockup/extract-fixtures.mjs W5N5          # add a room fixture from the private server (read-only)
```

- Rooms are fixtures (`scripts/mockup/fixtures/<room>.json`): real terrain and natural objects of the room and its 8 neighbours; rooms beyond are walled. Spawn spot = same `findSpawnSpot` as the harness.
- Reports in `test-results/mockup-*.json` (`world.points` = same definition as the harness; `world.storage` energy, `world.remoteRoads`, `world.creepsByRoom` census, `memorySize` by Memory key, `segmentSize` by segment id; the log prints `Memory <chars>` and `Segments`), compare summary in `test-results/mockup-compare-summary.txt` (points, RCL, storage).
- From-scratch runs reach the storage around tick 11k on W7N3 and 20k+ on W1N3 (W9N5: RCL 3 at 20k): measure storage-era changes with `TICKS=30000`.
- CPU: the mockup and the private server don't charge the official 0.2 CPU per intent. The bot counts successful intents (`src/utils/intents.ts`, counters `intents`, `intents:<method>`), and the reports print `Intents x/tick | official CPU estimate` (code CPU + 0.2 x intents) and `CPU by role (per tick / per creep)` (counters `cpu:<role>`, `creepTicks:<role>`).
- Don't start `compare.sh` twice at once: both write the same logs and summary.
- States: `--save-state` also saves every 2000 ticks (written atomically), so a run whose engine died can be resumed with `--load-state` + `--save-state` on the same file. On load every `user` reference but the NPCs ("2", "3") becomes the new user (controller reservations and signs included). With many containers at once the Docker VM runs out of memory and kills engine processes: the run then stops after 3 minutes without a tick (exit 2) instead of waiting forever.
- Not the full world: no other players, no backend/cron jobs. Use it to iterate, confirm on the private server before concluding.
- Speed-ups (default, `--no-fast` disables them all; checked on 3 rooms x 8000 ticks: same points within noise):
  - `scripts/mockup/fast.cjs` (preload, inherited by the engine child processes): no room history (`roomHistory:<room>`, replay data for the web client: the LokiJS storage answers each `hmset` with the whole hash, which grows without bound for rooms not active on a multiple of 20 ticks, so ticks got slower over a run: 16 ms/tick over 3000 ticks, 30-46 ms/tick over 8000 with 3-4 runs in parallel, vs 17-31 now) and no `mapView` writes; the runner fetches `users.code` (the 400+ KB bundle) once instead of every tick; the processor caches room terrain.
  - `sim.cjs` main loop: accessible rooms / room statuses refreshed every 20 ticks like the engine main loop (upstream mockup: every tick), no `tickStarted`/`roomsDone` notifications (backend only), CPU read from the runner `user:<id>/cpu` pubsub instead of a `users.findOne` per tick, storage RPC over a Unix socket, `--processors 2` engine processors (rooms of a tick processed in parallel, as on the private server; 3 brings nothing with ~2 active rooms).
  - Tried without gain: `--max-semi-space-size`. The rest is the bot (isolated-vm) and ~10 storage round trips per stage.
- `scripts/mockup/nodelay.cjs` disables Nagle on the storage RPC sockets (without it a tick takes ~280 ms); the vendored `screepsServer.js` passes `STORAGE_HOST=127.0.0.1` to child processes (Node 17+ resolves `localhost` to `::1`).

### Live inspection (`scripts/live-inspect.mjs`)

Read-only CLI over the history segments (see Memory): `node scripts/live-inspect.mjs [--server main|pserver] [--shard shard0]` fetches Memory and segments 6-7 through the official API (token from `screeps.json` `main.token`, header `X-Token`, never printed; pserver signs in with `pserver.email`/`password`; backs off on 429) and prints counter rates per 1000 ticks (mean and the last `--last 6` snapshots; `--match <regex>` or `--all` for other counters), per room energy per 1000 ticks (local / remote income, build / repair / upgrade / spawn spending, spawn energy and idle ticks by role), module and role CPU, the remote balance per source (harvested, delivered, cost, net, delivered/harvested) and the last `--spawns 20` spawns with their reason. `--file <report>-memory.json` decodes a mockup `--dump-memory` instead. Snapshots start 1000 ticks after the deploy.

### CI (`.github/workflows/ci.yml`)

GitHub Actions on push and pull requests to master. Job `build`: `npm install` (reproducible without a lockfile: `package.json` pins `@types/lodash` 3.10.2 and `@types/screeps` 3.3.8, and forces picomatch 2 to 2.3.1 through `overrides`; newer releases break tsc or rpt2), `npm run build`, `lint`, `compile`, `tests/pathCodec` and `tests/planner`. Job `mockup` (regression gate, TooAngel's idea): builds the `screepy-mockup` image with the buildx GHA cache (label from `run.mjs --image-hash`, so `ensureImage()` reuses it), then runs the built bundle 3000 ticks on W7N3 and W1N3 with the usual checks plus `--min-points` (1400 / 600: ~35% below the mean, only catches a gross break: single 3000-tick runs of one bundle spread by +-18%, W7N3 1614-2318 for the same bundle; the first GitHub runs failed gates of 1950 and 1750) and `--max-cpu 40` (CPU is wall clock in the sandbox: 9-13 on a quiet host, 43 on an overloaded one). Reports are uploaded as artifacts. Raise the thresholds when the economy improves. Mockup options: `--min-points <n>` (FAIL below n world points), `--image-hash`; container names and reports now carry a random suffix (two runs started in the same millisecond used to collide). Note: ESLint ignores files under `.claude/` (worktrees): lint a worktree with `npx eslint --no-ignore src`.

## Architecture

Design: `docs/superpowers/specs/2026-10-17-hivemind-economy-rework-design.md`. Exact Hivemind rules with `file:line` sources: `docs/hivemind/hivemind-{spawning,roles,construction}.md`.

### Game loop (`src/gameLoop.ts`, `src/ModuleManager.ts`)

The ModuleManager runs modules in order with a CPU budget (80% of the limit): `mandatory` modules always run (errors logged in `Memory.moduleErrors`, never rerun in the same tick), others support `runEvery`, `disabled`, `maxSkips` (forced after N CPU skips) and bucket throttling by `priority` (see CPU throttling). Per-module average CPU in `Memory.moduleState` (`avgCpu`, last ~10 runs: a snapshot, read spikes as spikes) and total CPU in the counter `cpu:module:<name>`; the memory size (`RawMemory.get().length`) is checked every 100 ticks.

| Module | Frequency | Role |
|---|---|---|
| RoomIntel | mandatory | Hostiles in every visible room: `room.memory.enemies` (`expires` = expected death of the last hostile), `defenseMode` |
| RoomPlanner | every 10 | Computes each owned room's plan once (segments 3-4, see Memory) |
| CreepRunner | mandatory | Runs every creep through the handler of its `memory.role` |
| SpawnManager | mandatory | Best spawn option per room, one creep per room and tick |
| RoomBuilder | every 20 | Construction sites from the plan, max 5 per room |
| RoomCleanup | every 100 | Removes other players' sites and structures from owned rooms, structures off the plan once it is final (`src/construction/RoomCleanup.ts`, see Construction) |
| Defense | every tick (priority always) | Towers (military target, heal, rampart repair under attack) and safe mode (`src/defense/`) |
| IntelManager | every tick | Static intel of every seen room, owned ones included (segments 1-2, see Memory: sources, controller, mineral, owner/reserver, source keepers; refreshed every 100 ticks while visible). Hostiles and invader cores only in RoomIntel (`hasInvaderCore()`). Room name helpers: `src/utils/rooms.ts` |
| RemoteMining | every tick (selection every 20) | Remote sources each owned room mines |

### Economy core

Convention everywhere (`src/core/options.ts` `getBestOption`): **higher priority wins**, then higher weight; negative priority is never chosen; ties go to the first option collected.

- **Roles** (`src/roles/`, registered in `roles/registry.ts`): `harvester` (bound to a source, stationary on its planned harvest position = source container once a transporter exists, delivers like a transporter before), `transporter` (90%/10% hysteresis, orders revalidated every tick), `builder` (works from 90% full, builds/repairs, upgrades when nothing to do, never harvests), `upgrader`, `brawler` (RCL < 4 defense), `guardian` (RCL 4+, holds the rampart closest to the hostiles). `remoteHarvester`, `remoteHauler`, `reserver` (`src/roles/remote*.ts`, `reserver.ts`; flee hostiles that can fight, `roles/flee.ts`). `claimer`, `pioneer` (expansion, `roles/claimer.ts`, `roles/pioneer.ts`). The scout registers its handler in its module.
- **Spawning** (`src/modules/SpawnManager.ts`, `src/spawning/spawnRoles.ts`): each spawn role returns options (priority, weight); if the best option can't be paid yet the room waits (no cheaper fallback). Bodies from `src/core/bodyBuilder.ts` (exact port of Hivemind's BodyBuilder, `MoveMode`). Modules ask for creeps with `spawnManager.requestSpawn({ id, roomName, body, priority, memory })` on the same scale (harvesters 4-6, builders 3-4, remote/claimer 3, scout 1).
- Spawn energy order and exit directions (`spawning/spawnPlacement.ts`, not in Hivemind; The International `room/commune/commune.ts` spawningStructuresByPriority and `spawningStructureOps.ts` findDirections, Overmind `hiveClusters/hatchery.ts`): `spawnCreep` drains harvester-bay spawns/extensions first (their harvester refills them), then the others closest to the base center first. The order is cached per room and refreshed when the spawn+extension count changes or after ~1000 ticks +-10%; it falls back to the engine order if a structure is missing. New creeps leave towards the free adjacent tile farthest from the center, with planned bay center / harvest / upgrader / parking tiles last; every walkable direction stays listed (cached per spawn, ~500 ticks). Mockup 20000 ticks on a heavily loaded host: W7N3 405k -> 437k (1 vs 1, the baseline lost runs to VM timeouts), W1N3 187k (mean of 2) -> 184k (1 run), W9N5 116k -> 114k (means of 3); `--preset rcl4` 3000 ticks: 208.9k -> 209.0k. Points within noise; total move intents +1% / +5% / +7%; `deliver:spawn` and `spawn:starved` unchanged. Kept as neutral, not a measured gain: re-measure on a quiet host with a per-role move counter.
- **Dispatcher** (`src/dispatcher/`): `sourceDispatcher` / `destinationDispatcher` with providers (container, drop, grave, storage, overfullExtension / spawn, bay, tower, controller container, workerCreep, storage, drop at the base center). A creep's order lives in `creep.memory.order`; "reservation" = priority penalty per creep holding the same order, indexed per tick in `src/core/roomState.ts` (`creepsWithOrder`, `setOrder`, `clearOrder`).
- **Room state** (`src/core/roomState.ts`): per-tick caches (creeps by role and home room, by duo / squad (`duoCreeps`, `squadCreeps`), structures by type), source/controller containers, storage location (plan center before the storage), path length storage location -> controller container (`controllerRefillPathLength`, shared by spawning and dispatcher, not cached while the container is missing), effective energy, bays.
- **Planner** (`src/planner/`): Hivemind steps (center, harvest positions, upgrader spot + controller container, exit corridors, core, harvest bays, extension bays, ramparts on the min cut around the protected structures (`minCut.ts`), safe area (`safe` tiles; nothing built outside), towers placed greedily by rampart coverage plus 0.5 x their cover of the core (spawns, storage) and built closest to the center first (not in Hivemind: far chokepoints pulled every tower 10-20 tiles away from the base on W29N7), roads to the ramparts, on-ramps, `link.controller` next to the upgrader spot (older plans get it added on load, no replan); after the bays the helper parking spot, 10 labs on Hivemind's stamp (2 `lab.source` within range 2 of every other lab; fewer kept when no stamp fits, Hivemind fails the variation), power spawn, nuker and observer), packed in the `plans` segment store (`roomPlanner.planMemory(room)`: `k` variation, `s` score, `done`). Variations (`listVariations`): a center ("weighted", then the tile farthest from walls in each cell of a 3x3 grid; a room with a spawn keeps its center next to it) x every combination of sources with or without a spawn in their bay; scored by `RoomPlanScorer.ts` (structures, upkeep, tower cover, ramparts near exits, travel distances). The first variation is stored at once (the economy needs a plan from tick 1), the others are tried over the next runs (CPU budget 50% of the limit) and the best replaces it while nothing but the first spawn is built; a room without spawn waits for the final plan before building. Bump `PLAN_VERSION` (`RoomPlan.ts`) to replan every room. `PLAN_VERSION` 4 added the labs and high level structures: a version 3 plan (W29N7 live) is not replanned but extended in place (`extendRoomPlan`: parking, labs, power spawn, nuker and observer on the free tiles of its safe area, nothing built moves; the run.mjs check rebuilds each fixture's v3 plan, extends it and checks nothing moved). Offline check: `node tests/planner/run.mjs [ROOM...]` (all variations, scores, defense geometry: ramparts, safe tiles, tower ranges to the center in build order, tower cover of the core and of the ramparts; ASCII plan of the best in `test-results/plan-<room>.txt`, ~22 ms per variation in node). Fixtures in `tests/planner/data/` (`W29N7` = the live room, `W29N7-live` with its existing spawn).
- **Construction** (`src/construction/RoomBuilder.ts`): Hivemind order — RCL 1 spawns; RCL 2+ extensions bay by bay, source and controller containers, swamp roads to sources/controller; RCL 3 harvester-bay extensions, towers, ramparts once a storage exists (main ones, then on-ramps; not during a safe mode > 2000 ticks; see Defense); RCL 4 storage, then every planned road once the storage is built; RCL 5+ links (controller, then source links farthest from the controller, then storage: with 2 sources RCL 5 = controller + 1 source, RCL 6 = both sources, RCL 7 = storage); RCL 6 terminal, extractor and mineral container; once every main rampart holds 500k x maxWallHealth[rcl] / 20M hits (Hivemind checkWallIntegrity: 50k at RCL 6), labs (`lab.reaction` first while 3 are allowed); nuker, power spawn, observer and factory only when enabled (`Memory.construction = { nuker, powerSpawn, observer, factory }`, all off by default, `construction/settings.ts`, Hivemind `settings.default.ts` constructNukers...; nothing fills, fires or uses them yet, the plan keeps their tiles) (Hivemind buildEndgameStructures, rules in `docs/hivemind/hivemind-endgame.md`). Mockup W7N3 `--preset rcl8 --labs`, 8000 ticks: the baseline built the power spawn, observer and factory and had a nuker site by tick 6000-8000; now none, labs unchanged, storage 89k -> 244k.
- **Idle once built** (Hivemind room-manager `builtAllStructures`): a room whose full pass leaves no site, places none and puts nothing off (a creep on an obstacle tile, the global site cap) is skipped (heap `completeRooms`) until its RCL, plan (`v`/`k`/`s`), structures (count and position sum: decay, destruction), home roads of the remote paths, a long safe mode, the construction settings or the wall-integrity gate (only re-checked when the endgame waited for it) change, else a full rescan every `CREEP_LIFE_TIME` +-10%. Counters `roomBuilder:scan` / `roomBuilder:idle`. Mockup: RCL 8 `--labs` 8000 ticks RoomBuilder 0.457 -> 0.053 CPU/tick; from scratch 20000 ticks the room is rarely complete (W7N3 0.47-0.51 -> 0.42, W1N3 half the runs idle).
- **Stale sites** (`construction/siteCleanup.ts`, The International `international/constructionSites.ts`): every 100 ticks the first tick each of our sites was seen is kept in `Memory.siteFirstSeen` (dropped when gone); a site older than 20000 + 5 x progress ticks is removed (counter `sites:removedStale`), freeing the room cap (5) and the global one (100) from sites in remotes given up, failed expansions or lost rooms. Never fires within 20000 mockup ticks; checked with a 300-tick limit (51 removals, no error).
- **Room cleanup** (`src/construction/RoomCleanup.ts`, module `RoomCleanup` every 100 ticks; Hivemind `room/room-manager.ts` cleanRoom :242-330 and dismantleUnwantedDefenses :504-525): in owned rooms without hostile creeps (`destroy()` returns ERR_BUSY then), other players' construction sites are removed and their structures destroyed at once, storage and terminal included (the ruin keeps their content and is looted by the dispatcher's grave source). `room.storage` also returns another player's storage: waiting to loot it first left the room at RCL 1 with progress 0 (mockup W7N3 with a 20k leftover storage; baseline d2de81b: still RCL 1 at tick 8000). Once the plan is final: unplanned walls (not novice walls, `ticksToLive`), and our extensions, labs, links and containers on a tile planned for another structure (or an extension, lab or link on a planned road). Never our spawns, towers, storage, terminal or ramparts. Counters `cleanup:<type>`. Not ported: Hivemind's rebuild order for a room at RCL 3+ that lost its spawn (tower ramparts and towers before the spawn).
- **Links** (`src/modules/Links.ts`, `roomState.ts` `linkNetwork`, rules in `docs/hivemind/hivemind-links.md`): planned `link.controller` next to the upgrader spot (older plans get it added on load, no replan), `link.storage` in the core, `link.source` in each harvester bay. Network per tick: source links "in" (want 0), controller link "out" (wants 800), storage link neutral. Every 3 ticks one transfer per room (biggest surplus or fullest neutral -> biggest shortfall or emptiest neutral, at least 200; counter `link:transfer`). Deviation: the request expires 150 ticks after the creep leaves the spawn (Hivemind: 70% of its life, ~450 ticks), so squads never wait long. Users: military squads (TOUGH, ATTACK, HEAL, RANGED_ATTACK; MOVE stays plain, bodies are sized for plain MOVE), guardians and emergency builders (Defense). ### Defense (`src/defense/`, Hivemind `room-defense.ts`, `manager.military.ts`, `process/rooms/owned/defense.ts`)

- `enemyStrength(room)`: NONE / WEAK (invaders only, or towers out-heal and walls hold) / NORMAL / STRONG / DEADLY, from the hostiles' attack and heal (boosts included), the towers, the energy capacity and the weakest planned rampart. `isWallIntact`: every planned main rampart built. `desiredWallStrength`: the threat-scaled target below (x2 during the safe mode cooldown); builders repair ramparts up to it (on-ramps to a tenth).

Target ((rcl-3) x 50)^2.5 + threat x 5 x rcl^2, at least 20k, at most maxWallHealth: 20k at RCL 3-4, 100k at 5, 276k at 6, 566k at 7, 988k at 8 without threat. The safe-mode multipliers are kept and on-ramps still get a tenth. `room.memory.threat` rises to the strength of a player attack that is NORMAL or worse (dismantle + melee x 1.2 + ranged x 3.5 + heal; invaders never count) and otherwise decays x0.9999 per tick. Ramparts are only placed once a storage exists (TI `needsStoringStructure`; Hivemind: RCL 3). New rooms start with a 20000-tick safe mode during which no rampart is built, so 20k from-scratch runs barely change. - Towers: shoot the hostile with the highest military priority (our damage minus its healing, times its value), only if it can't just drain them at the room edge; else heal wounded fighters (any wounded creep without enemies); else, from NORMAL enemies with half a tower of energy, repair the weakest rampart a hostile can hit. Towers repair nothing else.

- Spawn: remote defenders (spawn role `brawler`, see remote mining) and owned room defense (`roomDefense`): brawler below RCL 4, also during a safe mode (deviation: Hivemind waits for its last 500 ticks, so an early invader lived through the first room's 20000-tick safe mode); from RCL 4 and NORMAL enemies, up to 5 guardians (1 ranged per 4) at priority 5 and up to 5 emergency builders (priority 4) with 10000 energy. - Boosts (Hivemind room-defense getCreepBoosts): guardians ATTACK or RANGED_ATTACK, emergency builders WORK (repair), best compound in stock, tier at most the enemies' (no limit up to NORMAL enemies, as in Hivemind). See Labs and boosts.

### Military (`src/military/`, our own design, milestone 7 steps 1-2)

- Target: `Memory.military.attack = "<room>"` (by hand), else an automatic target (`targets.ts`, every 100 ticks, Harabi's ROI: durability x distance penalty / threat): strongholds (invader cores of level 1 to `maxStrongholdLevel`, default 1) within 2 rooms of our rooms or 1 of our remotes first; player rooms only with `Memory.military.auto = true` (default off: never attacks players without opt-in; durability = weakest rampart in M hits + 0.25 per tower, threat = the player's infamy + 1000 for an armed room within 5 rooms, current target halved, safe mode and failures of the last 20000 ticks skipped). Level 0 cores in our remotes stay with the remote defense ATTACKER, which now leaves strongholds (core level 1+) alone. The squad goes from the closest RCL 4+ room (`minRcl` to lower it), spawn role `military` (priority 3, effective energy >= 2000). Ends when the room has no spawn, tower or invader core left (success) or after 10 lost creeps.
- `intel.ts`: every 10 ticks, hostile rooms in sight (`Memory.military.rooms`: owner, RCL, towers, spawns, safe mode, weakest barrier, core level / deploy / collapse, creep damage and heal); infamy (`Memory.military.infamy`: energy value of each player's creeps seen in our rooms and remotes, x0.95 every 1000 ticks).
- `sizing.ts` (TI combat requests): threat = towers x 600 (close) or x 150 (edge, range 20+) + enemy creep damage; duo when its healer covers the edge damage and its attacker beats the enemy heal x 1.2, else quad; `Memory.military.squad = "duo" | "quad"` forces it. Automatic targets only when feasible: the front creep lasts 20 ticks of net edge damage, or 10 ticks of net close damage against towers that refill (strongholds: so level 1 needs ~RCL 7, nothing below). A duo that lost a pair against a room now sized for a quad hands over to a quad.
- `combat.ts`: worst damage on a tile next tick (every enemy tower focusing, melee within 2, ranged within 4) vs our healing; verdict safe (healing outpaces damage), rescue (survives 3 ticks), doomed.
- `duo.ts`: forming -> advance -> retreat (below 60% hits) -> advance (from 95%). The attacker only steps with the healer next to it; nobody steps onto a tile that kills it within 3 ticks, evaluated on the tile it really lands on (exit tiles carry creeps to the next room); when only the healer would be doomed the attacker goes in alone and comes back to be healed, which drains towers. In the room: towers, the invader core, spawns, then other structures, breaking the weakest ramparts on the way (path cost by hits). Trace: `[Duo]` log lines.
- `quad.ts`: 2 attackers (TOUGH + ATTACK) and 2 healers (HEAL, a RANGED_ATTACK per 3 HEAL), `memory.quad` / `memory.slot`. forming (home, refilled there when a healer or two members are lost) -> travel (loose chain, the leader waits for the others) -> engage: pack into a free 2x2 block a tile away from exits, then path the top-left tile on a 2x2 cost matrix (each tile = most expensive tile of its block, a structure costs the ticks the quad needs to break it, 255 where the block touches an exit) and move all four in the same direction; nobody moves while one is fatigued; a rampart or wall in the next block is broken first. Border drain first (state `drain`, towers seen or never seen): one attacker at a time (most hits, from 90%) stands on the exit tile and bounces between the rooms (a creep left on an exit tile changes room every tick), the towers spend a shot on it every other tick, the others heal it from the rally point; it steps back below 60%; over once the towers are seen empty (again after a retreat). Inside, while towers with energy out-damage our healing on the next step, the quad goes no closer and soaks shots on the block around (range 8) with the least tower damage. Retreat (as a packed block while 3+ tiles from the border, then each to a rally point 3 tiles inside the staging room; loose retreats left a member to die alone) when a member drops below 60% or could not walk to the closest exit under the net damage (+3 ticks); back from 95%. While holding, single swaps of two members: attackers next to the focus, the member with the most hits on the tile the towers and hostiles hit (they shoot the closest). Healing: each healer heals the member with the lowest expected hits (hits minus the damage expected on its tile), then counts its heal in (pre-heal). Attackers hit an adjacent fighter, the focus, or the weakest adjacent hostile structure; healers' ranged parts pick a mass attack when it beats a single shot. Trace: `[Quad]` log lines (slot, position, hits of each member, action).
- Mockup: `--enemy W8N3:3[:defenders[:ringHits]]` builds an enemy base (full towers, ramparts on spawn and towers, a ring of ramparts at range 5, no safe mode) run by `scripts/mockup/enemy-bot.js`; `--stronghold W7N4:1` an invader stronghold (engine bunker template, deploys at tick 5, the core refills its towers); `--preset rcl4|rcl5|rcl7` starts from a fast-forwarded room (storage, extensions, source containers). - Measured (mockup, `--preset rcl4` W7N3 against W8N3, mission set at tick 1, first squad creep at ~340; 1300 energy: duo attacker 8 ATTACK, quad attackers 3 TOUGH + 8 ATTACK, healers 4 HEAL (duo) / 3 HEAL + 1 RANGED (quad)): RCL 3 base (1 tower, 30k ring) destroyed at tick 1489 by the duo (1454 with the new code, forced), 1439 and 1457 by the quad, no loss; RCL 5 base (2 towers) at 2182 by the duo (2 lost), 1883 and 2190 by the quad (1 and 4 lost, all of old age: the first quad aged out a few ticks before the end in the second run). ### CPU throttling (`src/utils/throttle.ts`, Hivemind)

- Creeps (`CreepRunner`): below a role's `throttleAt` bucket its logic is skipped on a growing share of ticks (spread per creep by a Van der Corput sequence), on every tick below `stopAt`; every creep is skipped once the tick used 85% of `Game.cpu.tickLimit` (except on exit tiles). Thresholds: harvester/upgrader 0/2000, transporter 0/5000, remote harvester 2000/5000, defenders and reservers never, others 2000/8000. Counter `throttled:<role>`.
- Modules (`ModuleManager`, `priority`): `always` (mandatory, towers), `high` 500/5000 (remote mining), `default` 3000/8000, `low` 5000/9500 (scout, market): the interval is multiplied by the recent CPU use, this tick's use above half the limit and the bucket below `throttleAt`; stopped below `stopAt`. `Memory.moduleState[m].throttled` counts held-back ticks.
- Measured (W7N3, CPU limit 8, mockup): without throttling the bucket sits at 0 and the script is killed every tick; with it the bucket holds ~3000 and nothing is killed.
- Official CPU (W7N3, RCL 4 + 5 remotes, ~30 creeps): ~13 code + ~30 intents x 0.2 = ~19. Intents by type per tick: move 12, harvest 7.6, upgrade 3.9, reserve 2.4.
- Intents by role and method, mockup W7N3 ticks 10k-20k (27.6/tick): remote hauler moves 7.2, remote harvests 5.3, remote builder moves 2.7, reserves 2.3, upgrades 2.1, local harvests 2.0, transporter moves 1.6. Moves are one intent per tile walked (fatigued ticks and staying in place cost nothing), so they only drop with fewer trips.

### Pixels and CPU unlocks (`src/modules/Pixels.ts`, not in Hivemind)

- Off by default: `Memory.pixels = true` turns everything on, `{ generate, sell, buyUnlocks, unlock, keepPixels: 0, unlockStock: 1, maxCpuRatio: 0.8 }` single settings (a setting not listed keeps its default). `maxCpuRatio` is a Memory setting: `Memory.pixels = { maxCpuRatio: 0.7 }` (default 0.8; it was 0.6, and shard0 at 15 of 20 CPU with a full bucket never made a pixel).
- Generation (every tick): `Game.cpu.generatePixel()` when the bucket is full, `Memory.stats.cpuAvg` below `maxCpuRatio` x the limit, the remote CPU budget uncapped (`Memory.remoteMining.maxRooms` undefined) and no owned room with a hostile not yet expected dead. Energy first: while the budget caps the remotes, a full bucket is its signal to add a remote room, not spare CPU. Absent on the private server and the mockup (screeps 4.3.0): nothing happens there, so it is only checked offline (`node tests/pixels/run.mjs`, in CI).
- Refill: after a pixel `Memory.pixelState.refilling` makes `decisionBucket()` (`utils/throttle.ts`) return 10000 until the bucket is full again, the CPU average reaches 80% of the limit or the remote budget gets capped. A capped budget is the only one that adds rooms on a full bucket (`bucket > 9000`), so it always reads the real bucket; an uncapped one can only lower (CPU above 95% still applies, a refill bucket below 5000 is hidden, as intended), and the budget changes at most every 1000 ticks, so the flag is cleared long before a capped budget could raise. Every bucket decision reads it (creep and module throttling, remote CPU budget, upgrader count, visuals redraw, planner, reclaim); the panel, stats and reports show the real bucket. Without it a pixel stopped the "others" roles below 2000 and throttled them up to 8000, with the default modules, for the ~1000 ticks a 20-CPU account takes to refill.
- Market (every 100 ticks, account resources: `Game.market.deal` without a room): use a CPU unlock when full CPU is not unlocked or ends within an hour (never with a subscription: `unlocked` without `unlockedTime`; not again within 10 minutes, an unlock can take 5 minutes to apply); buy 1 from the cheapest sell order while the stock is below `unlockStock`, at most 105% of the history average, keeping the MarketManager's 10000 credit reserve; sell the pixels above `keepPixels` to the best buy order from 95% of the history average. Nothing without price history.
- Counters `pixels:generated`, `pixels:sold`, `cpuUnlock:bought`, `cpuUnlock:used`; the report gets a `Pixels` line (stocks, full CPU hours left, credits) while enabled.
- Not measured on shard0 yet: at a 20-CPU limit the bot uses ~15-19 official CPU from RCL 4 with remotes; with the 80% gate and the budget gate, pixels come once every possible remote room is mined and the CPU average stays under 16.

### Reports (`src/modules/Reports.ts`, Hivemind `process/report.ts`)

- Every `Memory.reports.interval` ticks (default 3000) a plain-text report, logged and sent with `Game.notify` (split on lines into messages under 1000 characters, numbered): GCL and each owned room's RCL % with rate and ETA, storage + terminal energy and its change, income (`work:harvest` / `work:remoteHarvest` deltas), then one line per owned room from the room counters of the history (snapshots taken since the last report plus the current period, energy per tick: income local / remote, spending build / repair / upgrade / spawn, creeps, ticks covered), CPU average / max (tick CPU sampled every tick from `Memory.stats.cpu`) and bucket min, global resets, module errors (`Memory.moduleErrors`) and role errors (`roleError:*`), throttled creep-ticks (`throttled:*`), creeps spawned / died, remotes per home (rooms, sources, cap, starved sources), defense (rooms with hostiles seen, safe modes, squad losses), expansion and attack. Empty lines are left out. Counter deltas only, no room scans beyond owned rooms; state between reports in `Memory.reportState` (~330 chars).
- Immediate alerts, checked every 100 ticks, each at most once per 5000 ticks: a room lost its last spawn, a room no longer owned, a controller downgrading in < 5000 ticks, a module with 3+ errors since the last check.
- `Memory.reports = false` (or `{ enabled: false }`) turns everything off, `{ interval: 500, alerts: false }` changes the interval / turns the alerts off.
- Cost (mockup W7N3, 3000 ticks, interval 500): 0.04-0.05 CPU/tick.

### Traffic (`src/modules/TrafficManager.ts`)

All movement goes through `trafficManager.requestMove(creep, pos, { range, priority })` (lower priority value = more important), backed by `screeps-cartographer`. `whenInRange(creep, range, target, action)` (`src/core/movement.ts`) registers the move — or the "stay in range" intent once there — every tick, then runs the action: working creeps must call it every tick so they are not shoved away.

- Stationary creeps (`TrafficManager.requestMove` `holdRange`, Overmind `Movement.park` / miner: no pathing once parked): a creep already in range (not combat, in a room with a controller, target off the edge) registers cartographer's stay intent directly with `move()`: its tile, then the adjacent walkable tiles still in range. Obstacles are computed once per room and tick, only for range > 0. Cartographer's `moveTo` used to clone a full CostMatrix (`find(FIND_STRUCTURES)`) and look at 8 tiles for every such creep, every tick. `roomBays` keeps its structure ids in the heap until the room's structure count or plan changes (~100 ticks). Harvesters skip the creep look on their own spot and the `harvest` call on an empty source. Mockup W7N3 `--preset rcl6`, 4000 ticks, runs side by side: CPU per creep harvester 2.73 -> 1.50, upgrader 1.46 -> 0.79, remote harvester 0.89 -> 0.55, transporter 1.81 -> 1.42 (remote hauler 0.73 / 0.72 as control); CreepRunner 25.3 -> 18.6 per tick on an overloaded host. Points and intents unchanged. From scratch, 20000 ticks: W7N3 405k -> 411k, W1N3 191k -> 186k, W9N5 101k -> 118k (single runs, the "after" runs CPU-capped); local mining 95.4 / 93.8 / 75.9% -> 95.0 / 94.5 / 79.5%.

### Memory (`src/utils/segments.ts`, `src/utils/MemHack.ts`)

- MemHack: Memory is parsed once per global and reused; the engine still serializes it every tick. `Memory.stats.memoryParse` = parse CPU of the global, `Memory.stats.heap` = `Game.cpu.getHeapStatistics()` (used + external, limit, ratio; every 10 ticks).
- Segment stores (`segmentStore(name, ids, writeDelay, legacy)`, inspired by Hivemind `utils/segmented-memory.ts`): big, rarely written data in RawMemory segments with the decoded copy in the heap, serialized only when changed. `intel` segments 1-2 (written at most every 100 ticks), `plans` 3-4 (written the tick they change), `remotePaths` 5 (every 20 ticks). `segmentsPreTick()` loads them at the start of the loop, `segmentsPostTick()` writes the changed ones. Callers use the accessors (`intelManager.getIntel/allIntel`, `roomPlanner.getPlan/planMemory`, `remotePath`) and call `touch()` after a change.
- The active segment list persists across ticks and global resets (engine), so after a reset the data is there on the first tick. Only the first tick after requesting them is not `ready`: `get()` then returns the legacy Memory copy or a pending object merged on load; the planner and the remote selection wait for `ready` (never replan on partial data).
- Migration: on load, the old `Memory.intel`, `Memory.rooms[r].plan` and `Memory.remoteMining.paths` are merged into the store, written, then deleted from Memory (checked lossless: mockup from a 20000-tick Memory dump, `--memory @dump`). Overflow (> 100 KB per segment) is logged and not written (counter `segments:overflow:<name>`).
- Mockup, 20000 ticks: Memory W7N3 15.7k -> 10.7k chars, W1N3 14.0k -> 9.8k, W9N5 13.6-14.0k -> 8.9k (segments 1.4-2k intel, 1.6-1.8k plan, 0.6-1.4k paths); points W7N3 422k / 406k, W1N3 183k / 181k, W9N5 113-139k / 119k (single runs on an overloaded host). Serialize + parse at that size: ~0.07 -> ~0.045 ms per tick (node), points and CPU in the noise. What is left: `stats` ~4k (counters), `creeps` ~3.5k (~110 chars per creep; the 40-55k measured on f6f9a8c were dead creeps, cleaned since lot A), `moduleState` ~1.2k.
- Heap caches with a lifetime (`remoteCostMatrix`, remote `inHeap`, room status, idle positions, expansion scores, refill and haul paths) expire after a +-10% jittered TTL (`utils/jitter.ts`), the stored remote paths after a per-source deterministic one (`jitterFor`): everything filled after a global reset no longer expires on the same tick.
- History (`src/utils/history.ts`, module `History`): segment 6 `history`, every 1000 elapsed ticks a snapshot (ring of 30): tick, ticks covered, average tick CPU, bucket and lowest bucket, the delta of every `Memory.stats` counter since the previous snapshot (zero deltas dropped, rounded), and per owned room RCL, progress, storage + terminal energy, creeps and the room counters (see the counters list). Segment 7 `historyDetail`: the last 50 spawns (tick, room, role, priority, weight, cost, parts, reason: the option's optional `reason`, declared on `SpawnOption` by module augmentation in `SpawnManager.ts`, else `had <n>` creeps of the role at home, plus `for <source>` for remote options, room energy and the runner-up option; external requests give their `reason` or id) and the remote balance per snapshot: per source key, energy harvested (remote harvesters), brought home (remote haulers, counted once per trip on entering home, from the source they come back from) and spawn cost (remote harvester on its source; reserver split over its room's sources; haulers and remote builders, one pool per home, split over the home's sources by travel time: an estimate). Encoding: key tables `k` (counters) and `rk` (room counters), counter sets as base-36 integers in table order (`"1a,,3k"`), the tables rebuilt at each snapshot; each store is trimmed (oldest first, counter `history:trimmed`) above 20000 chars. Room counters and the remote balance live in the heap between snapshots (not in `Memory.stats`, serialized every tick): a global reset loses the current period's part before it, the snapshot then records the ticks covered (`rd`). Two stores so each stays under 20 KB and the spawn log (written at most every 100 ticks) never rewrites the snapshots. Measured (mockup, 4000 ticks, `--preset rcl5 --claim W8N3:2`, 2 rooms, 10 remote sources): 3 snapshots, segment 6 4.2k chars (key tables 2.4k, ~480 chars per snapshot: ~17k for 30), segment 7 4.4k (spawn log 3.7k, ~230 per remote snapshot); `Memory.stats` +135 chars (new counter keys) and `moduleState.History`; module `History` 0.011 CPU/tick (W7N3 from scratch 3000 ticks: 0.010), points within noise (rcl5 614.1k / 613.1k, W7N3 2287 / 2136). shard0 (3 rooms, ~140 counters) should land near 20k for 30 snapshots: the trim keeps the newest that fit.
- MemoryCleanup and the intel cleanup run on elapsed ticks (heap timestamps), not `Game.time % n`: the modules are bucket-throttled and could skip the multiple.
