# Decisions: platform

Design notes and measurements moved out of CLAUDE.md on 2026-10-27 (verbatim). Features removed the same day are in `removed.md`.

## Game loop (`src/gameLoop.ts`, `src/ModuleManager.ts`)

The ModuleManager runs modules in order with a CPU budget (80% of the limit): `mandatory` modules always run (errors logged in `Memory.moduleErrors`, never rerun in the same tick), others support `runEvery`, `disabled`, `maxSkips` (forced after N CPU skips) and bucket throttling by `priority` (see CPU throttling). Per-module average CPU in `Memory.moduleState` (`avgCpu`, last ~10 runs: a snapshot, read spikes as spikes) and total CPU in the counter `cpu:module:<name>`; the memory size (`RawMemory.get().length`) is checked every 100 ticks.

| Module | Frequency | Role |
|---|---|---|
| RoomIntel | mandatory | Hostiles in every visible room: `room.memory.enemies` (`expires` = expected death of the last hostile), `defenseMode` |
| RoomPlanner | every 10 | Computes each owned room's plan once (segments 3-4, see Memory) |
| CreepRunner | mandatory | Runs every creep through the handler of its `memory.role` |
| SpawnManager | mandatory | Best spawn option per room, one creep per room and tick |

## CPU throttling (`src/utils/throttle.ts`, Hivemind)

- Creeps (`CreepRunner`): below a role's `throttleAt` bucket its logic is skipped on a growing share of ticks (spread per creep by a Van der Corput sequence), on every tick below `stopAt`; every creep is skipped once the tick used 85% of `Game.cpu.tickLimit` (except on exit tiles). Thresholds: harvester/upgrader 0/2000, transporter 0/5000, remote harvester 2000/5000, defenders and reservers never, others 2000/8000. Counter `throttled:<role>`.
- Modules (`ModuleManager`, `priority`): `always` (mandatory, towers), `high` 500/5000 (remote mining), `default` 3000/8000, `low` 5000/9500 (scout, market): the interval is multiplied by the recent CPU use, this tick's use above half the limit and the bucket below `throttleAt`; stopped below `stopAt`. `Memory.moduleState[m].throttled` counts held-back ticks.
- Measured (W7N3, CPU limit 8, mockup): without throttling the bucket sits at 0 and the script is killed every tick; with it the bucket holds ~3000 and nothing is killed.
- Official CPU (W7N3, RCL 4 + 5 remotes, ~30 creeps): ~13 code + ~30 intents x 0.2 = ~19. Intents by type per tick: move 12, harvest 7.6, upgrade 3.9, reserve 2.4.
- Intents by role and method, mockup W7N3 ticks 10k-20k (27.6/tick): remote hauler moves 7.2, remote harvests 5.3, remote builder moves 2.7, reserves 2.3, upgrades 2.1, local harvests 2.0, transporter moves 1.6. Moves are one intent per tile walked (fatigued ticks and staying in place cost nothing), so they only drop with fewer trips.

## Visuals (`src/visuals/`)

- Every owned room: the planned structures not built yet (opacity 0.3, drawn like the game's structures by `structures.ts`, ported from screepers/RoomVisual (MIT); planned roads as thin blue-grey dashed merged runs, joined to the built roads next to them, so they don't read as built roads; planned ramparts as faint unfilled outlines) and the outline of the planner's `safe` area (`planVisual.ts`, redrawn every 100 ticks or when the plan changes); a minimalist two-column table top left (`panel.ts`, every 5 ticks; thin bars green, orange then red only when something needs attention, empty rows left out): controller % and ETA (progress rate over 1000 ticks, heap), energy, storage, empire income from the `work:harvest` / `work:remoteHarvest` counters, CPU and bucket, mining efficiency (`MiningStats`, also a % above each source of the room, and per remote room); CPU top (the 3 most expensive modules and roles, CPU per tick over 1000 ticks from the `cpu:module:<name>` / `cpu:<role>` counters); creeps by role (short names), spawning and the role waiting for energy (`spawnManager.nextRole`), spawn queue (the 3 best options of the last evaluation with priority and weight, `spawnManager.queue`), construction sites; defense (enemy strength, towers energy), safe mode, remotes, plan while searching, expansion, attack.
- Spawn overlay (`spawnVisual.ts`, every tick, a few elements per spawn): above the game's spawn name on a dark backdrop, role, ticks left and a progress bar under the spawn while spawning; on the first idle spawn the role the room waits for with energy / cost and priority (`spawnManager.nextSpawn`), in orange.
- World map (`Game.map.visual`, redrawn every 20 ticks, export cached; Hivemind `map-visuals.ts`, The International `mapVisuals.ts`): `mapRemotes.ts` draws each selected remote source's path (`remotePath`, one point every 5 tiles, one color per home room, red under attack), a dot and a label `<net>/t · <travel>t · <n>H` (net from `sourceNet`, as the selection prices it) on a dark backdrop, on the first row around the source clear of the room's other labels (green with a remote harvester, grey while without one for less than 300 ticks since `servedAt`, orange after, red starved = `STARVED_TICKS` or under attack), invader cores, and per home room `remotes N/cap · spawn X%` at (25,46) in the home's color (orange when capped); `mapStrategy.ts` draws `RCL n` on owned rooms (25,7), an intel age dot per known room (45,5: green < 10k ticks, orange < 50k, red), the expansion target (solid line from the spawn room, faint dashed once claimed, dashed from support squads, `expand · <age>` at (25,14)), expansion failures of the last 100k ticks (red circles), the attack target (red line from each squad's spawn room, `attack (<reason>) · <states>` at (25,40)); texts on a dark backdrop. `mapThreats.ts`: owned and remote rooms with living hostiles (`room.memory.enemies`, not expired) get a red frame (orange when `safe`) and `hostiles · <ticks left>t` (+ player names and enemy strength while visible) at (25,33); remote rooms and the expansion target show their reservation at (25,7) (`res 3.2k` green when ours, orange below 1000 or older than 1500 ticks `?`, red with the name when someone else's, Invader included; `unreserved` dim where a home can reserve), from the controller when visible, else the freshest of `lastClaim` and intel, extrapolated. `mapCreeps.ts`: our creeps outside their home room (pioneers cyan, claimers violet, squads red, remote defenders orange, scouts grey, remote builders dark grey dot only), grouped by role / home / room / target / state, a dashed line to the target room and `<role> <state> x<n>` (pioneers filling / building / fetching, claimers travel / claiming).
- Map labels (`mapLabels.ts`): every map layer queues its texts with a priority (owned room texts, threats, home summaries, reservations, source labels, creeps) and the positions it accepts; they are placed in world coordinates (a label spilling into the next room counts) at the first free spot, and a source or creep label with none is left out (its dot keeps the color). Widths from Arial character metrics (`7.4/t · 54t · 1H` at font 6: 37.7 tiles computed, 38 measured on the client; a flat 0.42 per character overlapped the columns of room names). Fonts: RCL 6, other room texts 5, source / reservation / creep labels 4, `unreserved` 3.
- Map panel (`mapPanel.ts`, on by default): the map texts go to one table on a dark backdrop over the 3x3 source keeper rooms at the center of the first owned room's sector (never ours: remote mining and expansion skip keeper rooms; the label placer keeps out of it). A section per home room (`<room> RCL n remotes x/cap spawn y%`, one row per remote source: number, room, net/t, travel, harvesters, reservation, starved / attacked; sources numbered by home then travel time), an untitled one for expansion and attack, and `threats` (room, hostiles, ticks left, players, strength). The rooms keep the RCL, paths, source dots with their number, threat frames, expansion / attack circles and lines, and creep labels. `Memory.visuals = { mapPanel: false }` puts the texts back on the rooms. Homes in other sectors still go to the first one's panel. Checked offline (SVG render of the panel and labels from the compiled modules, sample world shaped like the shard0 screenshot) and in the mockup (`--preset rcl4`, 1500 ticks: no module error, RoomVisuals 0.54 CPU/tick); not seen in the client yet. Before, fonts 6-7 with a 20-tile width estimate checked within one room and one layer: on shard0 source labels, reservations and home summaries overlapped across rooms.
- Layers: `Memory.visuals = false` turns everything off, `Memory.visuals = { plan: false, panel: false, spawn: false, mapRemotes: false, mapStrategy: false, mapThreats: false, mapCreeps: false, mapPanel: false }` single layers (`settings.ts`, a layer not listed is on).

The module log splits `map` (redraws) and `mapImport` and counts the redraws. CPU pressure without the cap (2026-10-26; shard0 at 80-95% of 20 CPU, uncapped while the budget raises rooms, `cpu:module:RoomVisuals` 367-539 per 1000 ticks) and the slower panel: mockup W7N3 `--preset rcl4 --cpu-limit 13`, 4000 ticks, host at load ~20-25 (bucket below 2000 from tick ~1500 in every run, so nothing redrawn for long stretches), module 0.24 -> 0.19 CPU/tick (sequential runs, points 192.0k -> 189.0k) and 0.27 -> 0.15 (side by side, 197.3k -> 200.5k), no module error; no `--cpu-limit` (gate never on, cpuAvg ~23-25 of 100): 1.70 -> 1.84 wall-clock CPU/tick (host load), points 207.1k -> 204.3k. - Each room layer is cached as a `RoomVisual` export in the heap and imported on the other ticks. Priority `always` (a module skipped for a tick blanks the visuals: with `low`, the throttle skipped it every other tick as soon as the tick had used half the CPU limit, even with a full bucket); the layers are only redrawn above 5000 bucket (cached ones still imported) and nothing is drawn below 2000.
- Cost (mockup, W7N3 `--preset rcl4`, 3000 ticks): plan ~400-560 elements, room visual 52-69k chars, map 34 elements / 5.5k chars; module 0.15-0.25 CPU/tick, before and after the structure drawing, spawn overlay and map layers (side by side runs: 0.16 / 0.25, then 0.23 / 0.24-0.25; noise between runs of the same bundle is of the same order); the module logs sizes and CPU every 1000 ticks.

## Reports (`src/modules/Reports.ts`, Hivemind `process/report.ts`)

- Every `Memory.reports.interval` ticks (default 3000) a plain-text report, logged and sent with `Game.notify` (split on lines into messages under 1000 characters, numbered): GCL and each owned room's RCL % with rate and ETA, storage + terminal energy and its change, income (`work:harvest` / `work:remoteHarvest` deltas), then one line per owned room from the room counters of the history (snapshots taken since the last report plus the current period, energy per tick: income local / remote, spending build / repair / upgrade / spawn, creeps, ticks covered), CPU average / max (tick CPU sampled every tick from `Memory.stats.cpu`) and bucket min, global resets, module errors (`Memory.moduleErrors`) and role errors (`roleError:*`), throttled creep-ticks (`throttled:*`), creeps spawned / died, remotes per home (rooms, sources, cap, starved sources), defense (rooms with hostiles seen, safe modes, squad losses), expansion and attack. Empty lines are left out. Counter deltas only, no room scans beyond owned rooms; state between reports in `Memory.reportState` (~330 chars).
- Immediate alerts, checked every 100 ticks, each at most once per 5000 ticks: a room lost its last spawn, a room no longer owned, a controller downgrading in < 5000 ticks, a module with 3+ errors since the last check.
- `Memory.reports = false` (or `{ enabled: false }`) turns everything off, `{ interval: 500, alerts: false }` changes the interval / turns the alerts off.
- Cost (mockup W7N3, 3000 ticks, interval 500): 0.04-0.05 CPU/tick.

## Traffic (`src/modules/TrafficManager.ts`)

All movement goes through `trafficManager.requestMove(creep, pos, { range, priority })` (lower priority value = more important), backed by `screeps-cartographer`. `whenInRange(creep, range, target, action)` (`src/core/movement.ts`) registers the move — or the "stay in range" intent once there — every tick, then runs the action: working creeps must call it every tick so they are not shoved away.

- Move resolution (`src/core/traffic.ts` `resolveTraffic`, `TrafficManager.resolveRoom`, before `reconcileTraffic`): cartographer 1.8.16 (latest) claims tiles greedily, so a creep may claim the tile of an occupant that then gets no move, and swaps are only found when the occupant targets the claimer's tile; the engine drops a move into a tile whose occupant stays, and every move behind it. shard0 W28N7 (2026-10-21, RCL 4): two opposite flows through the one-tile diagonal (27,21)-(28,22) froze 15 creeps for 200-460 ticks, every one repathing each tick (`moveRetry` ~12/tick, CreepRunner ~15 CPU/tick at the 20 limit). Now each room with a conflict (a first target held by another creep, or wanted twice) is resolved from cartographer's intents (`getMoveIntents`): highest priority first, an occupant is pushed along its own intent (chains, swaps, rotations), a lower priority mover that can't advance steps back onto the pusher's tile (never onto an exit tile), failures memoized per root, at most 2000 push attempts per room and tick (then free tiles and swaps only); creeps whose tile differs from their first target are registered again with that one tile, then cartographer applies it. Rooms with pulls or blocked squares are left to cartographer; tired creeps without intent are never shoved; an exception keeps cartographer's result for the room (counter `traffic:error`). Counters `traffic:pushed`, `traffic:blocked`. Offline check `node tests/traffic/run.mjs` (in CI): the W28N7 fixture (live snapshot: room grid, each creep's goal, path and priority) over ticks, engine rules modelled: 12 of 12 movers at their goal by tick 48, 1 of 12 after 60 ticks with cartographer's algorithm; plus head-on, queue, rotation, holder, shove, priority step-back, dense block (36 creeps, 0.6 ms) and exit tile cases. Mockup 8000 ticks, 2 series of single runs on a loaded host (no one-tile choke in these rooms): points W7N3 129.6k -> 126.0k, W1N3 39.0k -> 36.3k, W9N5 5.4k -> 5.8k (signs change between series: noise), module TrafficManager +13-15% wall CPU on W7N3 / W1N3, -4% on W9N5, no module error. To confirm on shard0 (W28N7).
- Stationary creeps (`TrafficManager.requestMove` `holdRange`, Overmind `Movement.park` / miner: no pathing once parked): a creep already in range (not combat, in a room with a controller, target off the edge) registers cartographer's stay intent directly with `move()`: its tile, then the adjacent walkable tiles still in range. Obstacles are computed once per room and tick, only for range > 0. Cartographer's `moveTo` used to clone a full CostMatrix (`find(FIND_STRUCTURES)`) and look at 8 tiles for every such creep, every tick. `roomBays` keeps its structure ids in the heap until the room's structure count or plan changes (~100 ticks). Harvesters skip the creep look on their own spot and the `harvest` call on an empty source. Mockup W7N3 `--preset rcl6`, 4000 ticks, runs side by side: CPU per creep harvester 2.73 -> 1.50, upgrader 1.46 -> 0.79, remote harvester 0.89 -> 0.55, transporter 1.81 -> 1.42 (remote hauler 0.73 / 0.72 as control); CreepRunner 25.3 -> 18.6 per tick on an overloaded host. Points and intents unchanged. From scratch, 20000 ticks: W7N3 405k -> 411k, W1N3 191k -> 186k, W9N5 101k -> 118k (single runs, the "after" runs CPU-capped); local mining 95.4 / 93.8 / 75.9% -> 95.0 / 94.5 / 79.5%.

## Memory (`src/utils/segments.ts`, `src/utils/MemHack.ts`)

- MemHack: Memory is parsed once per global and reused; the engine still serializes it every tick. `Memory.stats.memoryParse` = parse CPU of the global, `Memory.stats.heap` = `Game.cpu.getHeapStatistics()` (used + external, limit, ratio; every 10 ticks).
- Segment stores (`segmentStore(name, ids, writeDelay, legacy)`, inspired by Hivemind `utils/segmented-memory.ts`): big, rarely written data in RawMemory segments with the decoded copy in the heap, serialized only when changed. `intel` segments 1-2 (written at most every 100 ticks), `plans` 3-4 (written the tick they change), `remotePaths` 5 (every 20 ticks). `segmentsPreTick()` loads them at the start of the loop, `segmentsPostTick()` writes the changed ones. Callers use the accessors (`intelManager.getIntel/allIntel`, `roomPlanner.getPlan/planMemory`, `remotePath`) and call `touch()` after a change.
- The active segment list persists across ticks and global resets (engine), so after a reset the data is there on the first tick. Only the first tick after requesting them is not `ready`: `get()` then returns the legacy Memory copy or a pending object merged on load; the planner and the remote selection wait for `ready` (never replan on partial data).
- Migration: on load, the old `Memory.intel`, `Memory.rooms[r].plan` and `Memory.remoteMining.paths` are merged into the store, written, then deleted from Memory (checked lossless: mockup from a 20000-tick Memory dump, `--memory @dump`). Overflow (> 100 KB per segment) is logged and not written (counter `segments:overflow:<name>`).
- Mockup, 20000 ticks: Memory W7N3 15.7k -> 10.7k chars, W1N3 14.0k -> 9.8k, W9N5 13.6-14.0k -> 8.9k (segments 1.4-2k intel, 1.6-1.8k plan, 0.6-1.4k paths); points W7N3 422k / 406k, W1N3 183k / 181k, W9N5 113-139k / 119k (single runs on an overloaded host). Serialize + parse at that size: ~0.07 -> ~0.045 ms per tick (node), points and CPU in the noise. What is left: `stats` ~4k (counters), `creeps` ~3.5k (~110 chars per creep; the 40-55k measured on f6f9a8c were dead creeps, cleaned since lot A), `moduleState` ~1.2k.
- Heap caches with a lifetime (`remoteCostMatrix`, remote `inHeap`, room status, idle positions, expansion scores, refill and haul paths) expire after a +-10% jittered TTL (`utils/jitter.ts`), the stored remote paths after a per-source deterministic one (`jitterFor`): everything filled after a global reset no longer expires on the same tick.
- History (`src/utils/history.ts`, module `History`): segment 6 `history`, every 1000 elapsed ticks a snapshot (ring of 30): tick, ticks covered, average tick CPU, bucket and lowest bucket, the delta of every `Memory.stats` counter since the previous snapshot (zero deltas dropped, rounded), and per owned room RCL, progress, storage + terminal energy, creeps and the room counters (see the counters list). Segment 7 `historyDetail`: the last 50 spawns (tick, room, role, priority, weight, cost, parts, reason: the option's optional `reason`, declared on `SpawnOption` by module augmentation in `SpawnManager.ts`, else `had <n>` creeps of the role at home, plus `for <source>` for remote options, room energy and the runner-up option; external requests give their `reason` or id) and the remote balance per snapshot: per source key, energy harvested (remote harvesters), brought home (remote haulers, counted once per trip on entering home, from the source they come back from) and spawn cost (remote harvester on its source; reserver split over its room's sources; haulers and remote builders, one pool per home, split by travel time over the home's sources with a remote harvester, and a container for haulers (all of them when none qualifies): an estimate), then since 2026-10-21 a steady flag, the home and window flags (`key=h,d,c,steady,home,flags`; flags base 36: 1 selected by that home the whole window without a global reset, 2 threat sample, 4 the container site next to the source made progress or was finished, `windowFlags`; a source selected the whole window with nothing to count gets a zero entry): every 10 ticks the History module samples each selected source (home, a living remote harvester, container standing, hostiles or invader core in the source room or the home, controller reserved by us when in sight); a window is steady when the source was selected by the same home on 90% of the expected samples, had a harvester and a container on 90% of them, no threat sample, one reservation state on 90% of the samples in sight and no global reset (`steadyWindow`). A source no longer selected keeps its last home (heap, `lastHome`; lost on a global reset), so `live-inspect` shows it as `<home> (dropped)`: its costs are those charged while it was still selected (spawn costs are charged on the spawn tick, never to an unselected source), its harvest and deliveries come from its creeps still alive. A source that changes home within a window mixes both homes' numbers and is not steady. Accessor `remoteBalanceWindows()`. Encoding: key tables `k` (counters) and `rk` (room counters), counter sets as base-36 integers in table order (`"1a,,3k"`), the tables rebuilt at each snapshot; each store is trimmed (oldest first, counter `history:trimmed`) above 20000 chars. Room counters and the remote balance live in the heap between snapshots (not in `Memory.stats`, serialized every tick): a global reset loses the current period's part before it, the snapshot then records the ticks covered (`rd`). Two stores so each stays under 20 KB and the spawn log (written at most every 100 ticks) never rewrites the snapshots. Measured (mockup, 4000 ticks, `--preset rcl5 --claim W8N3:2`, 2 rooms, 10 remote sources): 3 snapshots, segment 6 4.2k chars (key tables 2.4k, ~480 chars per snapshot: ~17k for 30), segment 7 4.4k (spawn log 3.7k, ~230 per remote snapshot); `Memory.stats` +135 chars (new counter keys) and `moduleState.History`; module `History` 0.011 CPU/tick (W7N3 from scratch 3000 ticks: 0.010), points within noise (rcl5 614.1k / 613.1k, W7N3 2287 / 2136). shard0 (3 rooms, ~140 counters) should land near 20k for 30 snapshots: the trim keeps the newest that fit.
- MemoryCleanup and the intel cleanup run on elapsed ticks (heap timestamps), not `Game.time % n`: the modules are bucket-throttled and could skip the multiple.
